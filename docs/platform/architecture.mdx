The platform separates **placement**, **VM lifecycle**, **image construction** and **guest capabilities**. Those responsibilities connect through explicit interfaces; a common product family does not make every artifact or protocol interchangeable.

<Diagram id="platform-context" title="Platform context and execution boundaries">
HostWeave assigns work to a host agent. Its GuestWeave adapter invokes a local CLI. Imageweave hands construction output to OCI tooling through a build manifest. Guest capabilities live behind agent core and its modules.
</Diagram>

## Responsibilities

| Area | Owns | Important boundary |
| --- | --- | --- |
| GuestWeave | Local VM lifecycle and host-specific execution | Separate macOS and Windows implementations |
| HostWeave | Control-plane APIs, placement and work execution coordination | Host agents execute through runtime adapters |
| Imageweave | Reviewed image scenarios, construction and qualification paths | Construction alone does not grant runtime acceptance |
| Agent core | Authenticated host services, module verification and supervision | Capability modules execute as separate processes |
| Agent modules | The module SDK and OS-specific capabilities | SDK and module releases have their own versions |

## Execution and agent roles

The HostWeave host agent is the process responsible for executing work assigned by the orchestration control plane. Its GuestWeave VM adapter invokes a `weave` binary and interprets the result. The agent core running in a guest is a different process: it supervises capability modules and brokers host/guest communication.

Document these roles separately. A box labelled only “agent” hides two different lifecycles and trust boundaries.

## Image and release dependencies

The shared OCI layer owns the Weave artifact format and artifact tooling. Release-channel data identifies promoted module and image versions. They appear in this first release as dependencies of the selected products rather than separate product documentation areas.

A build manifest, registry artifact, qualification result and promoted release are distinct objects. There is no verified universal build → publish → promote → run path in this baseline. The [compatibility register](compatibility.md) explains the current image-format gap.
