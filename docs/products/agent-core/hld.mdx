Agent core is the guest-side process owner and capability router used by the current macOS GuestWeave integration. The physical host's GuestWeave run process owns the VM and the other end of the channel. Inside the VM, `weave-agent` owns module processes, routes capability messages and supplies services to those modules.

Core also supports device/container contexts, including a Unix socket channel for containers. Windows GuestWeave's main baseline uses its own guest agent, described in its [HLD](../guestweave/windows.mdx). The separately inspected [Windows migration branch](../guestweave/windows-development.mdx) provisions shared core and OS modules instead.

## Process ownership

| Component | Runs where | Owns |
| --- | --- | --- |
| OS service manager | Guest/device OS | Starts the installed weaveboot service |
| `weaveboot` | Guest/device OS | Selects the current core, verifies staged updates, launches core and handles early crash-loop rollback |
| `weave-agent` | Guest/device OS | State, module discovery/reconciliation, registry, policy, identity, local control and capability-channel routing |
| Module supervisor | Inside core | Placement/privilege checks, verified launch, lifecycle, health/watchdog and bounded restarts |
| Capability module | Separate guest process | OS-specific feature implementation, such as command execution or clipboard |
| `weavectl` | Local authorised user | Calls core's control endpoint for status and lifecycle operations; Unix permits root or core's own UID |
| GuestWeave SDK client | Physical VM host | One channel owner per VM run; capability commands, registry and events |

“Host services” means core acting as the **module's runtime host**. These services execute inside the guest alongside core. Identity, storage and module supervision are not thereby moved onto the physical VM host.

## Interfaces and transport

| Interface | Direction | Encoding and purpose |
| --- | --- | --- |
| Module lifecycle | Core → module | Local gRPC/protobuf over Unix socket or Windows named pipe: Init, Start, Stop, Health, Shutdown |
| Host services | Module → core | Per-module local gRPC server: identity, store, policy, events, logging, registry, transport and watchdog |
| Capability channel | VM/container host ↔ core | Length-prefixed JSON envelopes: module address, kind, opaque payload and correlation ID |

The capability channel is a different wire from the lifecycle protobuf protocol. Protocol `1` does not establish compatibility with every host-channel vocabulary. Core's `internal/protocol/hvchannel` and the SDK's corresponding copy must encode compatible frames.

Configured socket transports are `vsock:<port>` on Linux, `hvsocket:<port>` on Windows and `unix:<absolute path>`. Default/auto probes the supported virtio-serial path. Core does not infer a socket listener merely because a socket facility exists. Invalid channel configuration disables the channel while allowing core to continue.

## Startup and module admission

Core creates the layout, probes capabilities, opens persistent storage and initialises identity. It assembles policy, registry, transport and host services, then reconciles the installed modules directory. Directory watches, reload signals and a configurable rescan trigger later reconciliation; the CLI's default rescan is one minute.

Admission follows this order:

1. Check the manifest's placement and required capabilities. Console-user placement requires user privilege; `per-user-all` placement is refused.
2. Stage the executable for its target identity and verify the actual path that will run.
3. Create its private run directory, random launch token and host-services listener. The listener is ready **before** the child starts.
4. Launch with the supported protocol window and IPC information. Read the single stdout handshake line and validate the selected protocol.
5. Dial its lifecycle endpoint and call Init with identity, configuration, capabilities, privilege and watchdog cadence. Recheck the requirements returned by Init.
6. Call Start and publish running state, protocol and surfaces to the registry. Monitor health, watchdog and process exit.

Core refuses duplicate channel addresses: delivery fans out to receivers at an address, so two owners of `weave.exec` could execute one request twice. An OS-specific installation ID such as `weave-linux-exec` can serve the stable `weave.exec` address.

## A capability request through the guest

GuestWeave's SDK client sends an addressed envelope. Core authenticates the external peer, resolves the module address and delivers the opaque payload through that module's transport receive stream. The capability service decodes the operation and calls its OS backend. Replies/events return through core to the SDK client, which correlates them with pending calls.

Core answers registry requests itself and publishes revisioned changes after authentication. Missing, non-running and overloaded modules can produce `delivery.failed`. A powered-on VM and a reachable core do not prove that the requested module is installed or serving.

## Trust boundaries

- **Executable admission:** the CLI supplies a platform verifier or signed-channel verifier. The lower-level `core.Run` refuses every module if no verifier is supplied. Linux's default release verifier checks root ownership and group/world write bits of the executable and its immediate parent. It assumes trusted installation provenance; it does not query package provenance or perform an exec-time cryptographic signature check.
- **Local module identity:** each host-services server binds a module identity to a random launch token, checked for unary and streaming RPCs. Store namespaces are fixed to that module.
- **External host authority:** the guest is provisioned with a public key and the VM host retains the private key. Core requires proof of possession before capability traffic and registry disclosure. Missing/malformed keys leave core running but operations refused. New connections authenticate again.

The external host key differs from the manifest root that verifies release/channel material. A successful hello establishes neither module provenance nor authority to execute commands.

## Durable state and updates

The layout separates durable state, module versions, staging, logs, runtime sockets and execution copies. `--state-dir`/`WEAVE_STATE_DIR` relocates the layout. `--modules-dir` changes both discovery and lifecycle installation. Installed modules have `current`, `previous` and `versions/<version>` entries.

The lifecycle manager serialises installation per module. Signed-channel installation checks channel signatures, artifact digest/size, expiry and sequence before staging and replacing a process. Local installation is a separate path using local files and the configured executable verifier; it does not perform those remote-channel freshness checks.

Channel fetching requires four HTTP-served bundle files: `manifest.json`, its signature, `signing.pub` and that key's signature. Selected artifacts are downloaded through the HTTP client. The separately inspected release-channel repository currently records bare OCI references and permits unsigned promotions; those entries do not directly satisfy this installer contract. See the [compatibility register](../../platform/compatibility.md).

For running modules, the default health gate requires healthy status for three seconds within a 30-second window. A console module waiting for a user session can be promoted **without a runtime health proof**; it starts when the session becomes available. Previous-version retention supports rollback. An unavailable sequence store refuses channel installs; a file marker alone cannot override that failure.

Core updates use a separate loop. weaveboot verifies a staged core, changes current/previous markers, then launches it. A readiness marker or sufficient stable uptime clears the early-crash counter; repeated early failures can restore the previous core. Readiness affects crash-loop recovery, rather than delaying the initial marker promotion. Core writes the marker after registering module runners and starting the control server goroutine; it does not wait for every module to start or confirm that the control listener has bound. The marker does not certify capability health.

## Failure behaviour

| Condition | Implemented response | Operational distinction |
| --- | --- | --- |
| Store already locked | Startup fails | Another core may own the store/channel/modules |
| Other store or identity failure | Core can run degraded, with dependent features unavailable | Liveness does not restore identity or durable queues |
| Modules directory unreadable on initial reconciliation | Startup fails | Broken installation differs from an empty directory |
| One invalid/unlaunchable module | Record its condition; other modules can start | Read the registry's state/detail for that module |
| No console user | Console-scoped module waits for a session | Clipboard/display absence can be expected placement |
| Repeated unhealthy polls or watchdog silence | Restart under supervisor policy and limits | Degraded health resets strikes rather than requesting restart |
| Channel/key unavailable | Guest operations unavailable; core can remain alive | Separate transport/authentication from module health |

This design follows the source lock. GuestWeave's installed payload versions have separate installer pins; no release-binary or host/guest runtime acceptance is claimed.
